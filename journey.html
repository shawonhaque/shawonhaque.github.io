Process

How I got here, and how I build now

Two related things: the order I learned the stack in, and the method I follow on every project. Neither is a list of job titles — it is the record of what I have actually built and the habits that came out of it.

The development journey

I learned this stack in one direction: foundations first, then the layers built on top of them. Each stage below is here because I built something with it, not because I read about it.

  1. Stage 01

    HTML and CSS — the structure underneath everything

    I started with semantic markup and modern layout: real landmarks, heading levels that mean something, flexbox and grid instead of floats and tables. Learning CSS custom properties changed how I think about a stylesheet — colours, spacing and the type scale became tokens, so a theme is a set of values rather than a second copy of the CSS.

    Built: the markup and full design system behind this portfolio.

  2. Stage 02

    JavaScript — making the page behave

    Then behaviour: the DOM, events, and the parts people get wrong — async flow, error handling, and knowing when not to reach for a library. I write progressive enhancement by default now: the page works without JavaScript, and the script only adds to it.

    Built: the theme system, navigation, scroll behaviour and contact form on this site — every one of them guarded, so a missing element never throws.

  3. Stage 03

    React — interfaces as components

    React was the shift from thinking about a page to thinking about state. Components, props, hooks, and lifting state to the right place. The habit I carried over from plain CSS turned out to matter here: reusable pieces and a clear separation between presentation and data access.

    Built: NEXORA, a React application with twenty page modules — see the case study.

  4. Stage 04

    TypeScript — making the compiler do the checking

    Types stopped being documentation and became a test that runs on every save. Strict mode, typed service boundaries, and a database schema typed all the way through to the components that read it.

    Built: NEXORA's service layer, where every call returns a typed result instead of throwing.

  5. Stage 05

    Node.js and Next.js — the direction I'm working in

    My current focus: server-side JavaScript, REST APIs and the rendering and routing model Next.js brings. This is where I am building now, and I would rather say that plainly than present it as years of experience.

    Working on: server routes and API design, applying the same habits from the layers below.

  6. Stage 06 · now

    Postgres and Supabase — data that enforces its own rules

    The stage that changed my thinking most. A database is not just storage: it is the one place a rule cannot be bypassed. Writing Row Level Security policies taught me that authorisation belongs next to the data, not in the client — and that a schema is a design decision, not an afterthought.

    Built: a seventeen-table schema, five migrations and RLS on every table in NEXORA.

How I build: my workflow

The same five stages every time. It is deliberately boring — the point is that nothing reaches the end without being checked.

  1. Planning — decide what "done" means

    Before any code: who is this for, what is the smallest version that is genuinely useful, and what will I check to know it works? On NEXORA the planning step is where I decided search would be extractive rather than generated, because a static front end cannot keep an API key secret. That one decision shaped the whole feature.

    • Scope
    • Acceptance criteria
    • Data sources

  2. UI design — the structure before the decoration

    I work from a small set of design tokens — colour, spacing, radius and a type scale — and lay out with grid and flexbox. Accessibility is decided here, not added later: heading order, focus states, contrast and what happens at 320px wide are all structural choices.

    • Design tokens
    • Responsive layout
    • Contrast
    • Keyboard order

  3. Development — small changes on a branch

    One concern per branch, one clear commit message. I keep the separation from the design step intact: markup, styles and behaviour stay in their own files, and reusable pieces become components rather than copies. Every new script checks for the elements it needs before using them.

    • Git branches
    • Semantic HTML
    • Reusable components
    • Typed boundaries

  4. Testing — check it where it will actually run

    This is the stage I have tightened most. I test at several viewport widths, in both themes, with reduced motion on, and with JavaScript disabled — and I compare the enhanced page against the plain one. I check the console, I follow every link, and I scroll the whole page to make sure no animation has left content invisible.

    When something is hard to check by eye, I measure it. The resume photo looked fine to me and was blank for other people, so the fix was verified in five independent PDF renderers instead of one.

    • Multiple viewports
    • Both themes
    • Reduced motion
    • JavaScript off
    • Console clean

  5. Deployment — publish, then verify the live result

    Changes go through a pull request, which is where I write down what changed and why — including what I decided not to do. After the merge I re-check the live site rather than assuming the deploy worked: the assets return 200, the console is clean, and the feature is actually running.

    I only claim something is shipped once I have seen it working at the real URL. "It works locally" is a statement about my machine.

    • Pull requests
    • GitHub Pages
    • GitHub Actions
    • Live verification

What the workflow is protecting

Five habits that the process above exists to enforce:

01

Nothing depends on an effect that might not run

Animation and enhancement are additive. Remove them and the page is still complete.

02

Never invent content

If the data is missing, say so. A clear empty state beats a plausible fake one.

03

Enforce rules where they cannot be bypassed

Access control belongs in the database, not in the interface that happens to call it.

04

Verify where it runs, not where you built it

Different renderers, different browsers, the live URL. Measure when you cannot see.

05

Ship less, but finish it

A smaller feature that is complete, accessible and tested beats a larger one that is nearly there.
