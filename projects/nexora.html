NEXORA — a knowledge platform that respects its sources

A multi-page React application that gathers reporting from established publishers, ranks it against a question, and keeps a personal library of what you save. The interesting part is not the interface — it is what the project refuses to do.

Overview

NEXORA is a knowledge platform with three jobs: show a live news dashboard, answer a question by searching what has been collected, and keep a private library of the articles, books and notes a person saves.

It is a real multi-page application, not a landing page. There are twenty page modules across thirty-three routes — home, explore, search, books, study, ideas, writing, profile, settings, an authenticated admin area and the rest — each one lazy-loaded so the first paint does not carry the whole application.

It is not a news organisation. It does not write, rewrite or editorialise. Every article links to the publisher's own page, and the source and timestamp shown come from that publisher's feed unchanged.

Problem and solution

The problem

Reading across many publishers means opening many tabs, and every one of them wants to keep you there. Meanwhile a "smart summary" feature is easy to fake: bolt a language model onto the front end, print something confident, and hope nobody checks the citation.

The solution

One dashboard with two honest data paths. Publisher feeds are fetched at build time into a static snapshot, because most news servers do not allow a browser to read their feeds directly. CORS-enabled APIs — Hacker News, Hugging Face, GitHub, Wikipedia — are called live in the browser, cached briefly, and spaced out to respect each provider's rate limit.

Search summaries are extractive: the sentences shown already exist in the retrieved articles, and each carries a numbered citation back to its source. Nothing is generated, so nothing can be invented.

Search does not call a language model, and the interface says so. That would need an API key, and an API key cannot be kept secret in a static front end. Adding a generation backend later means replacing one function, buildExtractiveSummary.

Key features

01

Live news dashboard

Ten publisher feeds in a build-time snapshot, plus four live APIs, with the collection time shown rather than implying second-by-second freshness.

02

Extractive search with citations

Sentences are selected from retrieved articles and each one carries a numbered reference to the source it came from.

03

Personal library

Saved articles, reading history, books and study material. Signed in, it is stored in Postgres under the reader's own identity; signed out, the same features run against localStorage and the interface states which mode is active.

04

Admin area behind Row Level Security

An authenticated dashboard for content, gated in the client for experience and enforced in the database for real.

05

Light and dark themes

Tailwind design tokens with a context provider, following the system preference until the reader chooses otherwise.

Architecture

A single-page React application with real routes, talking to Postgres through Supabase. Every layer has one responsibility, and the boundaries are typed. 

scripts/
  feeds.mjs      Fetch publisher RSS at build time → public/data/feeds.json
  postbuild.mjs  Copy index.html → 404.html for GitHub Pages deep links
src/
  components/    layout · news · ui · content — presentation only
  context/       ThemeContext, AuthContext (session + admin role)
  hooks/         useLiveData, usePersonalization, useAsyncData
  lib/           env, supabase client, typed schema, API cache, errors
  pages/         one file per route, lazy-loaded from router.tsx
  services/      typed data access; every call returns a Result
supabase/
  migrations/    0001 schema · 0002 RLS · 0003 storage · 0004 first admin
                 0005 personalisation

Two decisions that shaped the codebase

Every service call returns a Result. Nothing throws across a module boundary. A failure comes back as { data: null, error: { … } }, so a page can render an error state without wrapping every call in a try/catch. Backend calls also race a twelve-second timeout, so an unreachable project can never leave a page on a loading skeleton forever.

No placeholder records exist. The app previously fell back to hardcoded demo data when no backend was configured. That has been removed. An unconfigured or unreachable backend now produces a clear explanation — never invented content.

Security: the database is the control

Row Level Security is enabled on every table, and the policies are written so that access follows identity rather than trusting the client.

  • Admin checks are a database function. public.is_admin() reads request.jwt.claims, so a forged client-side flag means nothing.
  • Roles cannot be self-granted. A trigger rejects any role change unless the caller is already an admin and is editing someone else's row.
  • Personal data is private by construction. Interests, saved articles, reading history and notifications live in tables whose policies are scoped to auth.uid().
  • Untrusted text is never rendered as markup. Publisher summaries are stripped and decoded at build time, and links pass through a safeUrl helper that allows only http(s).

The client-side ProtectedRoute hides the dashboard from non-admins. It is there for experience, not for security — the policies are what actually stop an unauthorised read or write.

Challenges and what I learned

Feeds a browser is not allowed to read

The obvious design — fetch the news in the browser — fails, because most news servers send no CORS headers. Moving the fetch to build time solved it and taught me to be explicit about freshness: the interface shows the collection time instead of implying the data is live when it is a snapshot.

Deciding not to fake a feature

The easiest way to ship "AI search" would have been a prompt and a spinner. But a static front end cannot hold a secret, so the honest move was extractive search with citations — and to say in the interface that this is what it is. Learning to cut a feature rather than misrepresent it was the most useful thing in the project.

Where to enforce a rule

My first instinct was to guard the admin area in React. That is a UI convenience, not a control: anyone can call the API directly. Writing the real rule as a Postgres policy — and the client guard as a second, cosmetic layer — changed how I think about authorisation.
