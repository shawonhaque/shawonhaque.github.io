Islamic Life — a Bengali-first worship companion

One page that holds the whole Quran, prayer times computed on the device, qibla, tafsir, hadith, zakat and a worldwide mosque finder — written in Bengali first, working offline once loaded, and served as static files with no backend at all.

Overview

Islamic Life is a Bengali-first Islamic companion for the browser. It gathers what a practising Muslim reaches for through the day — the Quran, prayer times, qibla, tafsir, hadith, a tasbih counter, zakat, the hijri calendar, Ramadan and Hajj guides — into a single page that needs no account and no install.

The constraint that shaped everything else was hosting. The app is deployed to GitHub Pages, which serves files and nothing more. So the design question was never "which backend do I add", it was "how much of this can the browser do on its own". The answer turned out to be nearly all of it.

Problem and solution

The problem

Most Islamic apps in this space are either English-first with Bengali bolted on, or they lean on a server for things that do not need one: prayer times that could be arithmetic, Quran text that never changes, and a mosque list that is already public data. Each server dependency is a bill, an outage and a privacy question attached to a daily habit.

The solution

Push the work into the client. Prayer times are computed from coordinates with the standard astronomical formulas, so they are correct offline and in any timezone. The Quran is converted from its source snapshots at build time into static JSON, so reading it is a file fetch, not a query. And the mosque finder asks OpenStreetMap — a public dataset — for whatever the map is currently showing.

The rule for the whole app: if the browser can compute it, the server should not. That is what makes a static deploy of this size possible, and it is why the app still works on a weak connection once the first load has landed.

Key features

01

The whole Quran, in Bengali

All 114 surahs with Bengali translation and transliteration, shipped as static JSON and read straight from the bundle. Per-ayah audio plays through a single shared player.

02

Prayer times computed locally

Times come from the device's coordinates and a chosen calculation method — Karachi, MWL, ISNA, Umm al-Qura, Egyptian or Tehran — so they work with no network and no API key.

03

A mosque finder that works anywhere

The map viewport is the query. Pan to Cairo or London and the list refills from OpenStreetMap, with clustered markers, distances, Jumu'ah and phone filters, and one-tap directions.

04

Qibla, tasbih, zakat, hijri

A compass bearing to the Kaaba, a tap counter with presets and session history, a zakat calculator across gold, silver, cash and liabilities, and a hijri calendar with observances.

05

Optional cloud, honest fallback

Google sign-in adds cloud backup for settings and reading progress. Without it everything stays in localStorage, and a JSON export keeps the data portable.

Architecture

A React 19 and TypeScript single-page app, built by Vite into a static bundle. Heavy surfaces are code-split so the first paint stays small. 

src/
  components/    31 views and shared UI, heavy pages behind React.lazy
  contexts/      AuthContext, SettingsContext
  data/          seed content: knowledge, modules, curriculum
  utils/         prayer maths, qibla, search, mosque data, safe fetch
  three/         globe and qibla scenes, loaded on demand
  types/         shared domain types
data/quran/      114 surah snapshots, converted at build time
scripts/         build-time generators: Quran, brand, SEO, search index
server.ts        Express API for local development only
firestore.rules  rules so a user can only touch their own documents

Build-time conversion, not runtime work

The Quran snapshots are large and never change at runtime, so a build script converts them into the shape the reader wants and writes them to public/quran/. The app then fetches plain JSON. The same idea covers the brand assets, the SEO tags and the search index: work that would otherwise repeat on every visit happens once, at build time.

One dev server, no production server

server.ts is an Express process that proxies Vite in development so the AI endpoints can be exercised locally. It is never deployed. The production build knows it has no backend — a build flag switches the client off the /api paths and onto bundled data, so the same code runs in both places without branching across the components.

Code splitting by weight

Three.js, Leaflet and the AI studio are the expensive parts, and none of them belong in the entry bundle. Each sits behind React.lazy with a shared suspense fallback, so a visitor reading the Quran never downloads a 3D globe they will not open.

Challenges and what I learned

A mosque finder that was quietly local

The first version searched a fixed five-kilometre radius around the user. It looked correct in Dhaka and was useless everywhere else: stand in London and the app insisted there were no mosques. The bug was not in the rendering, it was in the question being asked.

The fix was to make the map the source of truth. The finder now takes the viewport's bounding box, queries that, and refetches when you move. Two details mattered: Overpass times out on continent-sized boxes, so an oversized viewport asks you to zoom in rather than hanging; and a mosque is often mapped twice in OpenStreetMap — once as a node for the point of interest and once as a way for the building — so entries sharing a name within 150 m are collapsed into one.

Public data sources fail in confusing ways

The Overpass API is free, which means it is busy. Mirrors answer 502 "at capacity" for minutes at a time, and some regional extracts answer 200 with an empty set for the rest of the world — indistinguishable, to the UI, from "there are no mosques here". That second one is the dangerous failure: a wrong answer looks exactly like a right one.

So the mirrors are raced rather than tried in turn, only planet-wide mirrors are allowed in the list, and the two empty states are kept separate: "nothing mapped here" is a different message from "the server is busy", with a retry button for the second.

Two languages, one layout

Bengali sets wider than English at the same font size, and its line breaking rules are its own. Every shared component is built with that in mind — flexible widths, no fixed heights on text blocks, and a language switch that changes copy without reflowing the page into a different shape.
