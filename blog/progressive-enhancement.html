Animation that is safe to remove

This site has a WebGL hero, smooth scrolling and scroll reveals. Turn any of them off — or turn off JavaScript entirely — and every page is still complete. That is the whole design rule.

The rule I set myself

It is easy to build a site that depends on its effects. The animations run, the content fades in, and it looks finished — until the JavaScript fails to load, the visitor has reduced motion turned on, or the device is too slow to keep up. Then the site does not degrade. It breaks.

Nothing on the page may depend on an effect that might not run. Every motion layer is additive. Remove any of them and the page is still readable, navigable and complete.

That single sentence decides most of the implementation questions before they come up: where the content lives, what the CSS does by default, and what the script is allowed to assume.

Content is visible before any script runs

The reveals animate elements from a state, they do not leave the page hidden waiting for script. The markup ships visible; the animation, when it runs, moves things into place. If the script never loads, nothing was ever hidden — there is no "content appears only after JS" failure mode.

I verified this the blunt way: load every page with JavaScript disabled and check that the text is present and at full opacity. It is. That test is part of how I check the site, not an afterthought.

The WebGL hero earns its place or does not appear

The constellation behind the hero is the most expensive thing on the page, so it has the most guards. Before it is even considered, the code checks three things and bails out on any of them:

  • Reduced motion. If the visitor asked for less motion, the scene is skipped entirely — not slowed down, skipped.
  • Small screens. On a phone the scene would be off-screen work and a large download for a decoration that adds little at that size.
  • No WebGL. A cheap canvas probe runs first, so the library is never fetched on a device that cannot use it.

Only then, and only once the hero is close to the viewport, is the renderer fetched — and that fetch is a dynamic import, so it is not part of the initial payload. 

// Fetch the renderer only once the hero is close to the viewport.
var loader = new IntersectionObserver(function (entries) {
  entries.forEach(function (entry) {
    if (!entry.isIntersecting) return;
    loader.disconnect();
    import(sibling("vendor/three.module.min.js"))
      .then(function (module) { initHeroScene(canvas, module); })
      .catch(function () { canvas.remove(); });
  });
}, { rootMargin: "200px" });

Notice the .catch. If the import fails — offline, blocked, or unsupported — the canvas is removed and the hero simply has no constellation. Nothing else on the page depends on it, so nothing else changes.

Smooth scrolling that does not break the page

Smooth wheel scrolling is the kind of feature that quietly breaks other things — anchor links, the sticky header, scroll-linked effects — if it is implemented by transforming a wrapper element. So the library used here eases the real scroll position instead. The scrollbar, the sticky header, the progress bar and the reveal observer all keep reading the same window.scrollY, and nothing else has to know.

It is also skipped when the visitor prefers reduced motion, and the page scrolls normally if the library failed to load — the code checks that the constructor exists before it uses it. 

if (!reduceMotion && typeof window.Lenis === "function") {
  lenis = new window.Lenis({ /* … */ });
}

Two conditions, and the page is correct with or without the result.

How I check it actually degrades

"It should degrade gracefully" is a claim, so I test it like one:

  • Load each page with JavaScript disabled and confirm the full content is present and visible.
  • Emulate prefers-reduced-motion: reduce and confirm the hero canvas is not rendered and the content is untouched.
  • Watch the console for errors on every page in both themes — a failed optional effect should be silent, not noisy.
  • Check the layout at 1440, 820, 560 and 390 pixels wide for anything that depends on a script to stop overflowing.

Motion is a nice thing to have. It should never be the thing that makes the page work. See the portfolio case study for the rest of the decisions behind this site.
