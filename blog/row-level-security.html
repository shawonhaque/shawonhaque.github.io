Row Level Security is the only authorisation I trust

In NEXORA, the React client never decides who may read or write a row. That decision belongs to Postgres, and it holds even if someone opens the browser console and talks to the API directly.

The problem with client-side rules

The easy way to hide an admin button is a conditional in the component: render it only when the signed-in user's role is admin. It looks like security and it is not. The browser is the visitor's machine. Anything the client can decide, the client can be told to decide differently — and the API will happily answer the request either way.

So the rule I set for NEXORA: the client may decide what to show, never what is allowed. Visibility is a convenience. Permission is a boundary, and boundaries belong on the server.

Row Level Security is the Postgres feature that makes this practical. Each policy is a condition the database checks on every row, for every query, after authentication. If no policy permits the row, it does not exist as far as that request is concerned.

The shape of the answer

Every table in the schema has RLS enabled and at least one policy. Across the seventeen tables there are twenty-seven policies, written in their own migration (0002_rls_policies.sql) so the rules are reviewable in one place rather than scattered through the schema.

The policies fall into three shapes, and naming them makes the whole file readable:

  • Public read, admin write. Published content — posts, categories, books, study resources — is readable by anyone, and only an admin may insert, update or delete.
  • Owner-only. A row belongs to one person. Bookmarks, ideas, diary entries and saved items are readable and writable only when auth.uid() matches the row's owner column.
  • Self-service profile. A profile is public to read, but only its owner may change it.

Nine of the policies lean on auth.uid(), which is the identity of the authenticated request — not a value the client sends. A caller cannot claim to be someone else by passing a different id, because the id is not theirs to pass.

Asking "is this user an admin?" safely

Many policies need the same question answered: is the current user an admin? Duplicating that check inside every policy would be a maintenance trap. So it lives in one function, public.is_admin(), defined as SECURITY DEFINER — it runs with the privileges of its owner rather than the caller.

That matters for a specific reason. Without it, a policy that reads the profiles table to check a role would itself be subject to the profiles policies, and the check could recurse. Running the helper with elevated rights, in a narrow and auditable function, breaks the loop. 

-- one place decides what "admin" means
create function public.is_admin()
returns boolean
language sql
security definer
stable
as $$
  select exists (
    select 1 from public.profiles
    where id = auth.uid() and role = 'admin'
  );
$$;

Every admin-only policy then reads the same way, and there is exactly one place to change if the definition of "admin" ever changes.

The hole RLS alone does not close

Here is the subtle part, and the reason I am glad I wrote it down. RLS controls which rows a request may touch. It does not, by itself, stop a user from updating a column they are allowed to reach — including the very role column the admin check depends on.

A user who can update their own profile could try to set role = 'admin' on themselves. If that succeeded, they would pass every admin policy. The row-level rule was satisfied; the privilege escalation happened anyway.

The fix is a trigger, prevent_role_self_escalation, that rejects any change to the role column unless the request is already coming from an admin. Row security and column protection are two different jobs, and this is the second one. 

-- RLS says which rows you may touch.
-- This says which columns you may change.
create trigger profiles_guard_role
before update on public.profiles
for each row execute function public.prevent_role_self_escalation();

How I convinced myself it works

A policy file is easy to write and easy to get subtly wrong, so I did not trust it on reading. I checked it the way an attacker would:

  • Signed in as a normal user and queried another user's private rows — the API returned nothing, not an error with data attached.
  • Attempted to update my own role to admin — the trigger rejected it.
  • Called an admin-only write as a non-admin — refused at the database, even though the client had no way to hide the button it never rendered.
  • Confirmed the anon key alone (no session) can read only what the public-read policies allow.

The test that taught me the most was the boring one: open the browser console, grab the public key, and call the API by hand. Every rule that lived in the client evaporated. The ones in Postgres held.

What I would tell another developer

Put the rule where the data is. RLS plus a single admin helper plus one escalation guard is not much code — but it means the security of the whole application no longer depends on every component remembering to check something. That is the difference between a rule and a hope.

The policies are public, in 0002_rls_policies.sql, so you can read them rather than take my word for it. For the wider build, see the NEXORA case study.
