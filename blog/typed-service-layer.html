A service layer that never throws

Every call in NEXORA comes back as a value, never as a thrown exception. The database can fail, the network can fail, and none of it can crash a component that forgot a try block.

Why exceptions were the wrong tool here

Throwing is the default way to signal failure, and it has a quiet problem: a thrown error is invisible in the type system. A function that returns Promise<Post[]> tells the caller nothing about the way it can fail. Forgetting the try block compiles cleanly, ships, and breaks in front of a user.

In a data-heavy application like NEXORA, most calls can fail for ordinary reasons — no session, no network, a row the policy does not permit. Those are not exceptional. They are part of the contract, and the contract should say so.

The rule: an expected failure is a return value, not an exception. If the caller can do something sensible about it, the type should force the caller to notice it.

One result type for every call

The whole layer funnels through a single wrapper in src/services/base.ts. Its job is to turn any outcome — success, a thrown error, or an unconfigured backend — into the same Result shape. 

export async function run<T>(fn: () => Promise<T>): Promise<Result<T>> {
  if (!isSupabaseConfigured) {
    return fail<T>(
      'Supabase is not connected yet. Add your project URL and anon key to enable live data.',
      'NOT_CONFIGURED',
      true
    );
  }
  try {
    return ok(await fn());
  } catch (error) {
    return fail<T>(toServiceError(error).message, toServiceError(error).code);
  }
}

Two things are worth pointing out. First, the try/catch exists in exactly one place, so no individual service has to remember it. Second, isSupabaseConfigured is checked before the call: running the app without a backend is a normal state, and it produces a readable message rather than a crash. That third argument marks the failure as retryable, which is the kind of detail a plain catch would lose.

Twelve services, one entry point

There are twelve domain services — authentication, profiles, posts, books, study material, bookmarks, diary, search, storage and so on — and all of them sit on the shared base module. The rest of the app imports from a single barrel file, services/index.ts; a component never reaches into a domain module directly.

That keeps the boundary honest. If a service needs to move or split, the change stays inside the layer; the pages that use it are untouched. And because every function returns the same Result, calling code looks the same whichever domain it is talking to.

  • Typed requests. Query options are typed too — PostQuery, BookQuery, StudyQuery — so a filter cannot be assembled from a loose object.
  • Typed responses. List endpoints return Paginated<T> with items, total, page, pageSize and hasMore — the shape a UI actually needs to render pagination.
  • One page size. DEFAULT_PAGE_SIZE is a single constant, so pagination is consistent across every list in the app.

A small function that prevents a real bug

Full-text search builds a PostgREST filter from user input, which is exactly the kind of place a character like % or a comma can change the meaning of a query. Rather than trust the caller, the base module exposes one helper and every search goes through it. 

/** Escapes characters that have meaning inside a PostgREST `or`/`ilike` filter. */
export function escapeFilter(value: string): string {
  return value.replace(/[%_,()\\]/g, (match) => `\\${match}`);
}

It is four lines, and it is the difference between searching for what the user typed and searching for something the user crafted. Small, boring, load-bearing — the pattern I keep coming back to.

What it costs

I will be honest that this is not free. Every call site has to handle the failure case, because the type will not let it ignore one. There is more code at the edges than a bare await would need.

What it buys is that failure is handled on purpose, in one consistent shape, instead of being forgotten until production. For an application where a missing session or an unconfigured backend is a normal Tuesday, that trade is worth it. Where it would not be — a purely local utility with no I/O — I would not reach for it.

The full layer is public: src/services. For how it fits the wider application, see the NEXORA case study.
