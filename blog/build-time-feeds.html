Writing · Build pipelines

The build is the safest place to call the network

NEXORA shows live news from 24 publishers. None of those requests happen in the visitor's browser. They run once, at build time, and the site loads the result as a static file.

  • 24Publisher feeds
  • 6Categories
  • 20Second timeout
  • 0Feeds fetched at runtime

It started as a constraint, not a plan

The obvious way to show news is to fetch the feeds from the page. It does not work. Browsers cannot read most news RSS feeds directly, because the servers do not send CORS headers — the request is blocked before a byte comes back. That is not a bug to work around; it is the publishers' default posture.

The build, however, runs in Node on GitHub Actions with open network access. No CORS, no origin, no browser. So the feeds are fetched there, once, and written to a JSON snapshot the site loads statically.

What looked like a limitation turned out to be the better architecture. No visitor waits on a publisher's server, and no publisher sees traffic from my site. The news section is as static and as fast as the rest of the page.

What the build does

A single script, scripts/feeds.mjs, holds a registry of 24 publisher feeds across six categories — world, technology, science, education, business and AI. Each entry keeps the feed URL, the publisher's homepage for attribution, and the category it maps to on the site.

For each source it fetches the feed with a twenty-second timeout and a custom user agent that identifies the bot, parses the items, and keeps at most twenty per feed. Then it de-duplicates by item id, sorts everything by publication date, and writes the whole snapshot to public/data/feeds.json.

One detail I care about: every item is real. The title, link, source and date all come from the publisher's own feed. Nothing is generated, summarised or invented — a rule that matters when the same project refuses to generate answers elsewhere.

One bad feed must not break the deploy

Twenty-four external servers is twenty-four ways to fail, and a publisher having a bad morning is not a reason to ship a broken site. So the fetches run with Promise.allSettled, not Promise.all: every source is attempted, and each one either resolves or is reported — it cannot take the build down with it. 

const results = await Promise.allSettled(
  FEEDS.map(async (source) => {
    const xml = await fetchWithTimeout(source.url);
    const parsed = parseFeed(xml, source);
    if (!parsed.length) throw new Error('no entries found');
    return { source, parsed };
  })
);

Sources that worked are listed; sources that did not are recorded in a failures array and named in a warning. The snapshot always reflects what was actually retrieved.

The case that decides whether you can trust the deploy

The interesting question is what happens when everything fails — no network on the runner, or every publisher down at once. Writing an empty snapshot would quietly replace a working news page with a blank one. That is the worst outcome, because it looks like a code bug and it destroys good data.

So the script handles it explicitly: if no items were fetched but a previous snapshot exists, it leaves that snapshot untouched and warns. The site keeps the last known-good news. 

if (!unique.length) {
  if (previous?.items?.length) {
    console.warn('feeds: every source failed; keeping the previous snapshot untouched.');
    return;
  }
  console.error('feeds: no items fetched and no previous snapshot exists.');
  process.exitCode = 1;
  return;
}

Only when there is nothing to fetch and nothing to fall back on does the build fail loudly. That is the one situation where a human should be told, so it is the one situation that exits non-zero.

Publisher markup is not consistent

Feed descriptions are messy. Some publishers send real HTML tags; others send entity-escaped tags — the literal text &lt;p&gt; — so that a naive strip leaves visible tag gibberish on the page. The script handles this with a specific sequence: strip, decode, strip again, decode again. Decoding after stripping only once would leave escaped tags exposed; the second pass catches what the first turned into markup.

It also strips script blocks outright and guards the entity decoder against invalid code points, so a malformed feed produces plain text rather than broken output. Small defensive choices, made once, that keep the news page clean without anyone watching it.

What I took from it

Move network work to where you control the failure. At build time I can set a timeout, retry nothing and keep the previous result, and decide deliberately what "total failure" means. In the browser I would be at the mercy of whichever publisher is slowest, on the visitor's connection, with no fallback.

The script is public: scripts/feeds.mjs. For how it fits the rest of the platform, see the NEXORA case study.
